# 유출 시스템프롬프트 분석하기

💡 이 스킬은 2026년 9월 공개된 **클로드 페이블 5.1 시스템 프롬프트 유출본**을 어디서 찾고, 어떤 순서로 읽어야 시간 낭비 없이 핵심(툴 목록·사용 지침·말투 규칙)만 뽑아낼 수 있는지 알려주는 스킬입니다.

## 이게 뭔가요?

우리가 챗봇에 질문을 쓰기 전에, 회사가 모델에게 미리 건네는 긴 설명서가 있습니다. 이걸 **시스템 프롬프트(system prompt)**라고 부릅니다.

쉽게 비유하면, 새로 온 아르바이트생에게 사장님이 첫날 건네는 업무 매뉴얼입니다. 손님이 무슨 말을 하든, 아르바이트생은 그 매뉴얼을 머릿속에 깔고 대답합니다.

```
[회사가 미리 넣어 둔 설명서] ← 우리는 평소에 못 본다
+
[내가 방금 친 질문]
↓
모델의 대답
```

우리가 보는 건 화살표 맨 아래, 대답뿐입니다. 위쪽 설명서는 가려져 있어서 "왜 이렇게 대답하지?" 싶은 순간이 생깁니다.

2026년 9월, **클로드 페이블 5.1**의 설명서 전체가 공개 저장소 두 곳에 올라왔습니다.

| 저장소 | 파일 | 크기 |
|---|---|---|
| asgeirtj/system_prompts_leaks | Anthropic/claude-fable-5.1.md | 7,810줄 · 405KB |
| elder-plinius/CL4R1T4S | ANTHROPIC/Claude-Fable-5.1.md | 2,195줄 · 269KB |

두 파일은 같은 내용을 다르게 정리한 판본입니다. 앞의 것은 줄바꿈을 살려 7,810줄이고, 뒤의 것은 한 줄에 더 많이 눌러 담아 2,195줄입니다. 글자 수로는 27만 자를 넘고, A4 용지로 뽑으면 150장 안팎입니다.

안에는 크게 세 덩어리가 들어 있습니다.

**① 툴 목록** — 모델이 쓸 수 있는 도구가 이름과 사용법까지 적혀 있습니다.

```
## bash_tool 컴퓨터에서 명령을 실행한다
## web_search 웹을 검색한다
## create_file 파일을 만든다
## memory_write 기억 파일에 적는다
```

**② 세부 지침** — 그 도구를 언제, 어떻게 쓰라는 규칙입니다.

```
## search_usage_guidelines 검색을 언제 하고 언제 참는가
## file_handling_rules 파일을 어떻게 다루는가
## artifact_usage_criteria 아티팩트를 언제 만드는가
```

**③ 행동 규칙** — 말투와 태도입니다.

```
## refusal_handling 무엇을 거절하고 어떻게 말하는가
## tone_and_formatting 말투와 서식
## user_wellbeing 이용자의 안전을 어떻게 살피는가
## evenhandedness 민감한 주제에서 한쪽으로 기울지 않기
```

세 덩어리가 한 파일에 이어져 있어서, 도구 → 사용법 → 태도 순서로 읽으면 흐름이 잡힙니다. ✅ 무료: 브라우저와 GitHub 접속만 있으면 확인 가능하고 별도 유료 도구는 필요 없습니다.

## 따라하기

1. **저장소 열기** — 위 표의 첫 번째 링크(`asgeirtj/system_prompts_leaks` 저장소의 `Anthropic/claude-fable-5.1.md`)를 엽니다. 깃허브 파일 화면 머리에 다음처럼 적혀 있습니다.

   ```
   7810 lines (6918 loc) · 405 KB
   ```

2. **Raw 원문 보기** — 화면 오른쪽 위 **Raw** 버튼을 누르면 꾸밈 없는 원문만 보입니다. 통째로 복사하기 편합니다.

3. **목차처럼 훑기** — 브라우저에서 `Ctrl + F`를 누르고 `##`를 검색하면 절 제목만 훑을 수 있습니다. 목차 대신 쓰면 됩니다.

4. **먼저 볼 4곳만 골라 읽기** — 전체를 다 읽을 필요는 없습니다.

   | 먼저 볼 곳 | 왜 |
   |---|---|
   | `## tone_and_formatting` | 왜 답이 그렇게 생겼는지 바로 이해된다 |
   | `## refusal_handling` | 어떤 요청이 왜 막히는지 알 수 있다 |
   | `# Tools` 아래 도구 목록 | 모델이 실제로 뭘 할 수 있는지 보인다 |
   | `## artifact_usage_criteria` | 문서·앱을 언제 만들어 주는지 기준이 나온다 |

5. **읽은 내용을 프롬프트 작성에 반영**
   - 이미 적혀 있는 걸 또 요구하지 않는다. 서식 규칙은 이미 길게 적혀 있어서 "표로 정리해 줘" 같은 구체적 요구는 효과가 있지만, "깔끔하게 써 줘"는 이미 있는 지침과 겹쳐서 보태는 게 없다.
   - 거절의 기준을 알면 질문을 고칠 수 있다. 막히는 이유가 주제 자체가 아니라 맥락이 빠져서인 경우가 많다. 목적과 상황을 먼저 적으면 같은 주제도 이야기가 이어진다.
   - 도구를 이름으로 부르면 빨라진다. 검색이 필요하면 "찾아봐"보다 "웹 검색해서 출처와 함께"라고 쓰는 쪽이 낫다.

## 활용 예시

- **답변 스타일이 이상할 때** → `Ctrl+F`로 `tone_and_formatting` 검색 → 원본에 이미 명시된 서식 규칙을 확인 → "표로 정리해 줘"처럼 규칙 밖의 구체적 요구로 프롬프트 수정
- **요청이 자꾸 거절될 때** → `refusal_handling` 절 확인 → 막히는 지점이 주제인지 맥락 부족인지 파악 → 목적·상황을 먼저 설명하는 방식으로 질문 재구성
- **모델이 검색을 안 할 때** → `# Tools` 아래 `web_search` 항목 확인 → "찾아봐" 대신 "웹 검색해서 출처와 함께 알려줘"처럼 도구 이름을 직접 언급

## 💡 아이디어

유출본에서 확인한 절 제목(`tone_and_formatting`, `refusal_handling`, `artifact_usage_criteria` 등)을 기준으로 자신만의 "프롬프트 체크리스트"를 만들어두면, 이후 다른 모델의 유출본이 나올 때도 같은 틀로 빠르게 비교·분석할 수 있습니다.

## 주의사항

- 이 파일은 앤트로픽이 공식으로 낸 문서가 아닙니다. 이용자가 모델에게서 끌어내 올린 **유출본**입니다.
- 시스템 프롬프트는 회사가 수시로 고칩니다. 올라온 시점의 판본이라 지금과 다를 수 있습니다.
- 추출 과정에서 일부가 빠지거나 형식이 달라졌을 수 있습니다. 두 저장소의 줄 수가 다른 것도 그래서입니다.
- 저장소의 이용 조건은 각 저장소 표기를 따라야 합니다. 내용을 그대로 옮겨 쓰는 것과 참고하는 것은 다릅니다.
- 정리하면, "모델이 이렇게 움직이는구나"를 이해하는 참고 자료로 보는 게 맞습니다. 규격서로 믿고 그대로 따라 만들 문서는 아닙니다.
