# 그래프 엔지니어링 판단 기준 12가지

💡 AI 에이전트들을 **조직도처럼 엮어** 병렬로 실행하는 '그래프 엔지니어링'의 **적합성 판단 기준 12가지**를 제시합니다.

## 이게 뭔가요?
최근 AI 프롬프트에서 '그래프 엔지니어링'이라는 용어가 자주 등장하고 있습니다. 이는 여러 AI 에이전트를 마치 조직도처럼 구성하여 동시에 작업을 처리하도록 하는 방식입니다. 개별적인 프롬프트보다 효율성을 높일 수 있다는 기대가 있지만, 잘못 사용하면 오히려 오류나 의도치 않은 결과를 초래할 수 있습니다. 이 문서는 그래프 엔지니어링을 어떤 작업에 사용해야 하고, 어떤 작업에는 피해야 하는지에 대한 12가지 판단 기준을 제시하며, 실제 실험 결과를 통해 그 효용성과 위험성을 분석합니다.

## 따라하기
### 1. 그래프 엔지니어링 직접 실험 결과
일곱 개의 작업 파일을 검수하는 작업을 두 가지 방식으로 진행했습니다. 첫 번째는 순차적인 개별 에이전트 방식, 두 번째는 일곱 개의 에이전트를 병렬로 실행하는 방식입니다. 지시문은 거의 동일했으나, 병렬 처리 시 예상치 못한 결과가 나왔습니다.

| 구분 | 순차 방식 | 병렬 방식 |
|---|---|---|
| 소요 시간 | 5분 45초 | 3분 40초 |
| 토큰 | 적음 | 자릿수가 달라짐 |
| 결과 형태 | 서술형 심층 | 점수표 + 우선순위 |

병렬 방식에서 시간은 단축되었지만, AI가 지시문에 없는 내용을 사실인 것처럼 지어내어 결과에 포함시키는 문제가 발생했습니다. 특히 '개선안을 하나씩 달라'는 지시에서 AI가 '없음'으로 끝내지 못하고 빈칸을 그럴듯하게 채워버린 것이 원인이었습니다. 이는 병렬 처리 시 속도뿐만 아니라 실수가 함께 증폭될 수 있음을 보여줍니다.

### 2. 그래프 엔지니어링 적용 판단 기준 12가지

**✅ 병렬로 돌려도 되는 작업 (1~4번)**
1.  **찾기:** 여러 파일이나 계정에서 패턴이나 키워드를 검색하는 작업. 기존 데이터를 기반으로 하므로 지어낼 여지가 적습니다.
2.  **판정:** 형식, 오탈자, 색상, 규격 등 기계적으로 체크 가능한 작업. 답이 명확하게 정해져 있습니다.
3.  **변환:** 번역, 포맷 변경, 요약 등 원문이 존재하여 나중에 대조가 가능한 작업.
4.  **수집:** 여러 소스에서 정보를 긁어와 각각 정리하는 작업. 입력 데이터가 외부에 있어 AI가 임의로 생성할 여지가 적습니다.

**✅ 병렬로 돌리면 안 되는 작업 (5~8번)**
5.  **창작:** 없는 것을 새롭게 만들어야 하는 작업. AI가 빈칸을 임의로 채울 가능성이 높습니다.
6.  **개인화:** 개인의 경험이나 의견이 필요한 작업. AI가 알 수 없는 정보를 지어낼 수 있습니다.
7.  **추론:** 근거 없이 결론을 내려야 하는 작업. 에이전트마다 다른 결론을 도출할 수 있습니다.
8.  **순차 의존:** 앞선 결과가 뒤따르는 작업의 입력으로 사용되는 경우. 본질적으로 병렬 처리가 불가능합니다.

**✅ 실행 조건 (9~12번)**
9.  **작업이 5개 이상일 것:** 작업 수가 적으면 병렬 처리의 이점보다 나누는 비용이 더 클 수 있습니다.
10. **개당 2~3분은 걸릴 것:** 짧은 작업 여러 개를 병렬로 처리하면 오버헤드가 더 많이 발생합니다.
11. **지시에 '개선안', '만들어줘' 등을 포함하지 말 것:** 창작을 유발하여 오류의 원인이 됩니다.
12. **결과에 1인칭 문장이 있으면 전수 확인할 것:** AI가 본인의 경험인 것처럼 허위 정보를 생성할 수 있습니다.

### 3. 복붙 프롬프트 예시 (클로드)
```
워크플로우 써서 아래 N개를 병렬로 처리해줘.
항목당 독립 에이전트 하나씩 붙이고, 마지막에 결과를 합쳐줘.

[항목 목록]

각 항목마다: [기계적으로 판정 가능한 지시]
해당 사항이 없으면 '없음'이라고만 쓰고 새로 만들지 마.
```

*   **주의:** '워크플로우 써서'를 명시해야 클로드가 병렬 에이전트 기능을 호출합니다.

### 4. 지어낸 내용을 걸러내는 법
1.  결과에서 1인칭 문장('제가', '저는', '~했어요' 등)을 모두 찾습니다.
2.  찾은 문장이 실제로 사용자가 한 말인지 원본과 대조합니다.
3.  근거 없이 내려진 단정적인 문장을 의심합니다.
4.  여러 에이전트가 비슷한 문장을 생성했다면, 이는 같은 빈칸을 각자 채운 것이므로 더욱 의심해야 합니다.

### 5. 알아두면 좋은 것
'그래프 엔지니어링'은 새로운 이름일 뿐, 앤트로픽의 'Building Effective Agents'(2024) 등에서 논의된 Orchestrator-workers, Parallelization 패턴과 유사합니다. 초기 아이디어는 2026년 6월에 언급되었고, 'graph engineering'이라는 용어는 2026년 7월에 커뮤니티에서 탄생했습니다. 이 방식은 '조직화된 무의미'를 대규모로 생산할 위험도 지적되고 있습니다.
