# 그래프 엔지니어링 적용 기준 수립 (합병됨)

## 이게 뭔가요?

최근 AI 분야에서 '그래프 엔지니어링'이라는 용어가 자주 등장하고 있습니다. 이는 여러 AI 에이전트를 마치 조직도처럼 구성하여 동시에 작업을 처리하도록 하는 방식입니다. 개별적인 프롬프트를 순차적으로 실행하는 대신, 복수의 에이전트를 병렬로 운영함으로써 작업 속도를 향상시키고 효율성을 극대화하는 것을 목표로 합니다. 

하지만 잘못 사용하면 오히려 오류나 의도치 않은 결과를 초래할 수 있습니다. 본 글에서는 그래프 엔지니어링을 직접 실험해보고, 어떤 작업에 적합하며 어떤 작업에는 피해야 하는지에 대한 구체적인 판단 기준 12가지를 제시합니다. 이를 통해 사용자는 AI 에이전트의 병렬 처리를 더욱 효과적으로 활용할 수 있습니다.

### 직접 재본 결과

일곱 개의 작업 파일을 검수하는 작업을 두 가지 방식으로 진행하여 시간과 결과를 비교했습니다. 지시문은 거의 동일했으나, 작업 방식만 다르게 설정했습니다.

| 구분 | 순차 방식 | 병렬 방식 |
|---|---|---|
| 소요 시간 | 5분 45초 | 3분 40초 |
| 토큰 | 적음 | 자릿수가 달라짐 |
| 결과 형태 | 서술형 심층 | 점수표 + 우선순위 |

실험 결과, 병렬 처리 시 소요 시간이 단축되었으나, 일부 결과에서 AI가 사실이 아닌 내용을 지어내는 문제가 발생했습니다. 특히 '개선안을 하나씩 달라'는 지시에서 AI가 '없음'으로 끝내지 못하고 빈칸을 그럴듯하게 채워버린 것이 원인이었습니다. 이는 병렬로 돌리면 속도뿐만 아니라 실수 또한 함께 증폭될 수 있음을 보여줍니다.

## 따라하기

### 1. 병렬로 돌려도 되는 작업 (찾기, 판정, 변환, 수집)

*   **찾기**: 여러 파일이나 계정에서 특정 패턴이나 키워드를 검색하는 작업. 기존 데이터를 기반으로 하므로 지어낼 여지가 적습니다.
*   **판정**: 형식, 오탈자, 색상, 규격 등 기계적으로 체크 가능한 작업. 답이 명확하게 정해져 있습니다.
*   **변환**: 번역, 포맷 변경, 요약 등 원문이 존재하여 나중에 대조가 가능한 작업.
*   **수집**: 여러 소스에서 정보를 긁어와 각각 정리하는 작업. 입력 데이터가 외부에 있어 AI가 임의로 생성할 여지가 적습니다.

### 2. 병렬로 돌리면 안 되는 작업 (창작, 개인화, 추론, 순차 의존)

*   **창작**: 없는 것을 새롭게 만들어야 하는 작업. AI가 빈칸을 임의로 채울 가능성이 높습니다.
*   **개인화**: 개인의 경험이나 의견이 필요한 작업. AI가 알 수 없는 정보를 지어낼 수 있습니다.
*   **추론**: 근거 없이 결론을 내려야 하는 작업. 에이전트마다 다른 결론을 도출할 수 있습니다.
*   **순차 의존**: 앞선 결과가 뒤따르는 작업의 입력으로 사용되는 경우. 본질적으로 병렬 처리가 불가능합니다.

### 3. 실행 조건 (5개 이상, 개당 2~3분 소요, 특정 지시문 제외, 1인칭 문장 확인)

*   **작업이 5개 이상일 것**: 작업 수가 적으면 병렬 처리의 이점보다 나누는 비용이 더 클 수 있습니다.
*   **개당 2~3분은 걸릴 것**: 짧은 작업 여러 개를 병렬로 처리하면 오버헤드가 더 많이 발생합니다.
*   **지시에 '개선안', '만들어줘' 등을 포함하지 말 것**: 창작을 유발하여 오류의 원인이 됩니다.
*   **결과에 1인칭 문장이 있으면 전수 확인할 것**: AI가 본인의 경험인 것처럼 허위 정보를 생성할 수 있습니다.

### 4. 복붙 프롬프트 예시 (클로드)

```
워크플로우를 사용하여 아래 N개를 병렬로 처리해줘.
각 항목마다 독립적인 에이전트를 하나씩 할당하고, 마지막에 모든 결과를 합쳐줘.

[항목 목록]

각 항목마다:
[기계적으로 판정 가능한 지시]
해당 사항이 없으면 '없음'이라고만 쓰고 새로 만들지 마.
```

*   **주의**: '워크플로우 써서'를 프롬프트에 명시해야 Claude 등 일부 AI는 병렬 처리를 수행합니다. 사용자가 명시적으로 요청하지 않으면 에이전트를 사용하지 않는 경우가 있기 때문입니다.

### 5. 지어낸 내용을 걸러내는 법

1.  결과에서 1인칭 문장('제가', '저는', '~했어요' 등)을 모두 찾습니다.
2.  찾은 문장이 실제로 사용자가 한 말인지 원본과 대조합니다.
3.  근거 없이 내려진 단정적인 문장을 의심합니다.
4.  여러 에이전트가 비슷한 문장을 생성했다면, 이는 같은 빈칸을 각자 채운 것이므로 더욱 의심해야 합니다.

## 💡 아이디어

그래프 엔지니어링은 단순 반복 작업 자동화뿐만 아니라, 복잡한 의사결정 과정을 여러 에이전트의 협업을 통해 시뮬레이션하는 데 활용될 수 있습니다. 예를 들어, 다양한 시장 분석 에이전트가 동시에 작동하여 최적의 투자 전략을 도출하거나, 여러 전문가 에이전트가 협력하여 복잡한 기술 문제를 해결하는 시나리오를 구상할 수 있습니다. 다만, 이 과정에서 AI가 생성하는 정보의 정확성과 신뢰성을 검증하는 절차가 필수적입니다.

## 주의사항

*   **지어낸 정보 경계**: 결과에서 1인칭 문장이나 근거 없는 단정을 포함한 내용을 발견하면 의심해야 합니다. 특히 여러 에이전트가 유사한 내용을 생성했다면, 동일한 '빈칸'을 각자 채운 것일 수 있습니다.
*   **병렬 처리의 함정**: 속도 향상만큼이나 실수나 오류도 함께 증폭될 수 있음을 인지해야 합니다. 결과 검증은 필수입니다.
*   **개념의 유사성**: '그래프 엔지니어링'은 새로운 이름일 수 있으나, Orchestrator-workers, Parallelization 패턴과 유사합니다. 초기 아이디어는 2026년 6월에 언급되었고, 'graph engineering'이라는 용어는 2026년 7월에 커뮤니티에서 탄생했습니다.
*   **대규모 무의미 생산 가능성**: 에이전트가 에이전트를 검사하는 과정에서 '조직화된 무의미'를 대규모로 생산할 위험이 있습니다. 결과물의 질적 관리가 중요합니다.

## 알아두면 좋은 것

'그래프 엔지니어링'은 새로운 이름일 뿐, 앤트로픽의 'Building Effective Agents'(2024) 등에서 논의된 Orchestrator-workers, Parallelization 패턴과 유사합니다. 초기 아이디어는 2026년 6월에 언급되었고, 'graph engineering'이라는 용어는 2026년 7월에 커뮤니티에서 탄생했습니다. 이 방식은 '조직화된 무의미'를 대규모로 생산할 위험도 지적되고 있습니다.
