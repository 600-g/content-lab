# Opus 4.8 풀세팅 가이드

💡 Opus 4.8은 모델만 바꿔서는 체감이 약하고, **effort 레벨**과 **프롬프트 구조**, Claude Code의 **Dynamic Workflows·Ultracode**를 함께 맞춰야 성능이 제대로 나옵니다.

## 이게 뭔가요?

Claude Opus 4.8은 Opus 4.7을 기반으로 코딩·추론·컴퓨터 조작·지식 업무 성능을 끌어올린 모델입니다. Anthropic은 이전 모델 대비 "완만하지만 체감할 수 있는 개선"이라고 설명합니다. 동시에 Claude Code에는 Dynamic Workflows, Ultracode, `/deep-research` 같은 새 기능이 들어왔습니다.

다만 Opus 4.8은 **설정값을 함께 바꿔야 성능이 극대화되는 모델**입니다. 아래 3가지를 같이 봐야 합니다.

| 구분 | 의미 | 실전 영향 |
|---|---|---|
| Model | Opus 4.8 자체 성능 | 기본 추론력, 코딩력, 글쓰기 품질 |
| Effort | 얼마나 깊게 생각할지 | 속도, 비용, 품질 차이 |
| Workflow | 작업을 어떻게 쪼개서 실행할지 | Claude Code 대형 작업 성능 |

이번 업데이트에서 사용 방식에 영향을 주는 특징은 4가지입니다.

- **Effort 설정**이 핵심 레버가 됨
- 프롬프트를 **더 문자 그대로 해석**함
- **도구 호출보다 먼저 자체 추론**하려는 경향이 있음
- 코딩·디자인·리뷰 작업에서 세팅 방식이 달라짐

### 성능 변화 (Opus 4.7 → 4.8)

| 평가 항목 | 영역 | Opus 4.7 | Opus 4.8 | 변화 |
|---|---|---|---|---|
| SWE-Bench Pro | 코드 작성 | 64.3% | 69.2% | +4.9%p |
| Terminal-Bench 2.1 | 터미널 작업 | 66.1% | 74.6% | +8.5%p |
| Humanity’s Last Exam | 추론 | 46.9% | 49.8% | +2.9%p |
| OSWorld-Verified | 컴퓨터 조작 | 82.3% | 83.4% | +1.1%p |
| GDPval-AA | 지식 업무 | 1,753 | 1,890 | +137 |
| Finance Agent v2 | 금융 분석 | 51.5% | 53.9% | +2.4%p |

Terminal-Bench 2.1에서는 GPT-5.5가 Opus 4.8보다 높은 점수를 기록했습니다. "모든 벤치마크에서 GPT-5.5를 앞섰다"는 설명은 정확하지 않습니다.

### 신뢰성·장시간 작업 개선

- 자신의 작업에서 불확실한 부분을 더 자주 표시합니다.
- 충분한 근거가 없는 주장을 할 가능성이 줄었습니다.
- 자신이 작성한 코드의 결함을 발견하고도 말하지 않고 넘어갈 가능성이 Opus 4.7 대비 약 4배 낮습니다.
- 장시간 에이전트 코딩 안정성, 긴 대화·긴 작업 맥락 처리 능력이 좋아졌습니다.
- 작업 중 컨텍스트 압축 후 원래 작업을 이어가는 능력이 향상됐고, 필요한 도구 호출을 건너뛰는 경우가 줄었습니다.

### 새로 생긴 기능 한눈에

| 기능 | 어디서 | 한 줄 요약 |
|---|---|---|
| Effort Control | Claude 웹 / Cowork 모델 선택 화면, Claude Code | 추론 자원 조절 (low · medium · high · extra(xhigh) · max) |
| Dynamic Workflows | Claude Code | 큰 작업을 서브에이전트로 분배 → 검증 → 통합 |
| Ultracode | Claude Code (`/effort ultracode`) | effort `xhigh` + 중요한 작업에 Dynamic Workflow 자동 구성 |
| `/deep-research` | Claude Code 내장 Workflow | 병렬 검색 · 출처 수집 · 교차 검증 · 인용 보고서 |
| 대화 중 system 메시지 | Messages API | `messages` 배열 중간에 `system` 역할 삽입 |
| Fast Mode | Opus 4.8 | 최대 2.5배 빠른 출력 속도 |

💰 유료 필요: Claude Opus 4.8 모델과 Claude Code 고급 기능은 유료 요금제 구독 또는 API 사용이 필요합니다. Dynamic Workflows 같은 신규 Claude Code 기능은 유료 사용자에게 제공됩니다.
✅ 무료 대안: 모델 자체를 대체하기보다, 이 가이드의 **프롬프트 구조화** 원칙(목표·맥락·성공 기준 명시)은 다른 모델에서도 그대로 적용할 수 있습니다.

## 따라하기

### 1. Effort 먼저 맞추기

Opus 4.8에서 가장 먼저 만질 것은 effort입니다. 낮으면 빠르게 답하고 사용량이 적고, 높으면 더 깊게 추론하고 토큰을 더 씁니다. 환경에 따라 **low, medium, high, extra (xhigh), max** 단계를 쓸 수 있고, Claude Code에서는 그 위에 Ultracode 모드가 있습니다. 이 문서에서 "X High"는 extra(xhigh), "Ultra Code"는 Ultracode를 가리킵니다.

#### 작업별 추천 effort

| 작업 유형 | 추천 effort | 이유 |
|---|---|---|
| 짧은 문장 수정 | Low / Medium | 빠른 응답이 더 중요 |
| 번역, 짧은 요약 | Medium | 비용과 속도 균형 |
| 콘텐츠 기획 | High | 맥락 이해와 구조화 필요 |
| 긴 문서 분석 | High / X High | 놓치는 정보 줄이기 |
| 코드 디버깅 | X High | 원인 추적 필요 |
| 복수 파일 수정 | X High | 파일 간 연결성 확인 필요 |
| 대형 리팩토링 | X High / Max | 구조적 판단 필요 |
| 앱 전체 구현 | Ultra Code | workflow·subagent 활용 |
| 코드 리뷰 | X High | 버그 탐지 깊이 필요 |
| 단순 질문 답변 | Low / Medium | 과추론 방지 |

#### 레벨별 사용법과 예시 프롬프트

**Low** — 짧고 범위가 명확한 작업에만 씁니다. 복잡한 작업을 Low로 돌리면 표면적인 답만 나올 수 있습니다.
```
이 문장만 자연스럽게 바꿔줘.
아래 문장을 3줄로 요약해줘.
```

**Medium** — 비용과 속도가 중요한 반복 작업에 적합합니다.
```
아래 고객 리뷰 30개를 긍정/부정/개선요청으로 분류해줘.
아래 문장을 인스타 캡션용으로 조금 더 자연스럽게 다듬어줘.
```

**High** — 대부분의 실무 작업 기본값입니다.
```
아래 내용을 바탕으로 인스타 캐러셀 기획안과 캡션을 만들어줘.
아래 시장조사 내용을 요약하고, 실무자가 바로 실행할 액션 아이템으로 바꿔줘.
```

**X High (extra / xhigh)** — 코딩, 에이전트, 복잡한 분석 작업의 기본값입니다.
```
이 코드베이스에서 로그인 오류가 발생하는 원인을 추적하고 수정 계획을 세워줘.
아래 5개 문서를 비교해서 공통 인사이트와 충돌하는 내용을 정리해줘.
```

**Max** — 정말 복잡한 작업에서만 테스트합니다. 토큰 증가 대비 효용이 줄고 과도하게 생각할 수 있어, High/X High로 부족할 때 올리는 옵션입니다.

**Ultra Code (Ultracode)** — Claude Code에서 대형 작업을 맡길 때 쓰는 고강도 모드입니다. 설정 방법과 동작은 4절에서 다룹니다.
```
이 프로젝트에 결제 플로우를 추가하고,
프론트엔드/백엔드/DB/에러 처리/테스트까지
전체 구현 계획을 세운 뒤 단계별로 진행해줘.
```

### 2. 프롬프트 기본 구조 잡기

Opus 4.8에서는 "대충 해줘"보다 목표·맥락·성공 기준을 분명히 주는 것이 중요합니다.

```
목표:
[이 작업을 통해 얻고 싶은 최종 결과]
현재 상황:
[지금 상태, 배경, 문제점]
원하는 결과물:
[형식, 분량, 톤, 파일 형태, 사용 목적]
성공 기준:
[좋은 결과라고 판단할 기준]
작업 방식:
1. 먼저 현재 상황을 진단해주세요.
2. 그다음 작업 계획을 제시해주세요.
3. 필요한 경우 단계별로 실행해주세요.
4. 마지막에 검수 체크리스트를 제공해주세요.
주의사항:
[금지 표현, 브랜드 톤, 기술 제약, 비용 제약 등]
```

#### "하지 마" 대신 "이렇게 해"

Opus 4.8은 지시를 문자 그대로 잘 따릅니다. 부정 지시만 잔뜩 넣기보다 원하는 방향을 구체적으로 알려주는 편이 안정적입니다.

나쁜 예시:
```
너무 장황하지 않게 해줘.
AI 티 나게 쓰지 마.
뻔하게 만들지 마.
```

좋은 예시:
```
답변은 핵심만 5개 항목으로 정리해주세요.
각 항목은 2문장 이내로 작성해주세요.
실무자가 바로 실행할 수 있는 표현을 사용해주세요.
추상적인 조언보다 구체적인 행동 지침을 우선해주세요.
```

#### "왜"를 같이 주기

목적을 알면 결과가 좋아집니다. 용도·타깃·기대 효과를 함께 적습니다.

카피 작업:
```
이 문장은 인스타그램 캐러셀 첫 장에 들어갈 후킹 문장입니다.
목표는 사용자가 스크롤을 멈추고 다음 장을 넘기게 만드는 것입니다.
너무 과장된 표현은 피하고, "나도 해당되나?"라는 느낌이 들게 바꿔주세요.
```

디자인 작업:
```
이 디자인은 AI 실무 팁을 공유하는 인스타 캐러셀 표지입니다.
타깃은 대학생, 크리에이터, 1인 사업가입니다.
너무 개발자 문서처럼 딱딱하면 안 되고,
저장하고 싶은 프리미엄 가이드 느낌이 나야 합니다.
어두운 배경, 큰 타이포, 작은 라벨, 명확한 CTA 구조로 제안해주세요.
```

#### 응답 길이 지정하기

Opus 4.8은 작업 복잡도를 보고 스스로 응답 길이를 조절하는 경향이 있어, 원하는 길이를 명확히 써주는 것이 좋습니다.

짧게 받고 싶을 때:
```
답변은 5줄 이내로 작성해주세요.
배경 설명은 생략하고, 바로 실행할 수 있는 항목만 주세요.
예시는 1개만 포함해주세요.
```

깊게 받고 싶을 때:
```
표면적인 요약이 아니라,
원인 → 구조 → 실행 방안 → 주의사항 순서로 분석해주세요.
각 항목마다 실무 예시를 포함해주세요.
```

콘텐츠용으로 받고 싶을 때:
```
인스타그램 저장형 콘텐츠에 맞게 작성해주세요.
문장은 짧게 끊고, 한 문단은 2~3줄을 넘기지 마세요.
전문 용어는 필요한 경우에만 쓰고, 바로 아래에 쉽게 풀어 설명해주세요.
```

#### 도구 사용 조건 명시하기

Opus 4.8은 도구를 무조건 먼저 쓰기보다 자체 추론으로 해결하려는 경향이 있습니다. 최신 정보·파일 확인·코드베이스 분석이 필요하면 조건을 명시합니다.

최신 정보 확인용:
```
이 작업은 최신 정보 확인이 중요합니다.
답변하기 전에 공식 문서 또는 신뢰할 수 있는 최신 자료를 먼저 확인해주세요.
확인한 정보와 추정한 정보를 구분해서 작성해주세요.
```

코드 작업용:
```
답변하기 전에 관련 파일을 먼저 읽어주세요.
추측으로 원인을 단정하지 말고,
실제 코드에서 확인된 내용과 가능성 있는 가설을 구분해주세요.
```

자료 분석용:
```
첨부된 문서를 먼저 기준 자료로 삼아주세요.
문서에 없는 내용은 외부 지식으로 보완하되,
문서 기반 내용과 보완 내용을 구분해주세요.
```

#### Thinking 깊이 조절하기

Opus 4.8에서 thinking은 기본적으로 꺼져 있을 수 있습니다. 버그 원인 분석, 문서 간 충돌 검토, 장기 계획 수립, 법률·계약·비용 검토, 대규모 코드 수정 전 설계 같은 복잡한 추론에서는 adaptive thinking을 켜는 방향을 고려하되, 지연 시간이 늘 수 있으니 아무 때나 켜지 않습니다.

깊게 생각해야 할 때:
```
이 작업은 다단계 추론이 필요합니다.
답변하기 전에 문제 구조를 신중하게 검토하고,
확실한 내용과 확인이 필요한 내용을 구분해주세요.
```

빠르게 답이 필요할 때:
```
이 작업은 단순 조회성 작업입니다.
불필요하게 길게 추론하지 말고,
바로 핵심 답변만 제공해주세요.
```

### 3. Claude Code 기본 작업 루틴

처음부터 "다 고쳐줘"라고 던지지 말고 다음 순서로 진행합니다: 현재 구조 파악 → 문제 원인 후보 정리 → 수정 계획 작성 → 필요한 파일만 수정 → 테스트 또는 검증 → 남은 리스크 정리.

```
목표:
이 프로젝트에서 [기능명/문제명]을 해결하고 싶습니다.
작업 방식:
1. 먼저 관련 파일과 현재 구조를 파악해주세요.
2. 아직 코드를 수정하지 말고, 변경 계획을 먼저 제시해주세요.
3. 변경 범위가 과도하면 더 작은 단위로 쪼개주세요.
4. 승인 후 필요한 파일만 수정해주세요.
5. 수정 후 테스트 방법과 검수 체크리스트를 제공해주세요.
성공 기준:
- 기존 기능이 깨지지 않아야 합니다.
- 수정 이유가 명확해야 합니다.
- 실제 실행 가능한 코드여야 합니다.
- 남은 리스크가 있다면 숨기지 말고 알려주세요.
```

### 4. 대형 작업: Dynamic Workflows · Ultracode · Subagent

#### 어떤 방법을 언제 쓰나

| 상황 | 쓸 것 | 비용 |
|---|---|---|
| 한두 파일, 범위가 좁은 수정 | 3절 기본 루틴 + "subagent 만들지 말 것" 지시 | 낮음 |
| 여러 파일·여러 책임 영역, 직접 분해를 지시하고 싶을 때 | Dynamic Workflows 분해 프롬프트 | 중간~높음 |
| 세션 전체를 대형 작업 모드로 돌릴 때 | `/effort ultracode` | 높음 |
| 여러 출처를 교차 검증하는 조사 | `/deep-research` | 높음 |

#### Dynamic Workflows란

하나의 큰 작업을 여러 작은 작업으로 나누고, 여러 서브에이전트에게 분배한 뒤 결과를 검증하고 통합하는 Claude Code 기능입니다. Claude가 작업에 맞는 JavaScript 스크립트를 생성하고, 이 스크립트가 에이전트 실행 순서·병렬 처리·반복 작업·조건 분기를 관리합니다.

- 실행 흐름 예시 (프로젝트 보안 문제 찾기): 전체 작업을 여러 보안 영역으로 분리 → 각 영역 담당 서브에이전트 실행 → 발견된 문제를 별도 에이전트가 검토 → 검증된 결과만 정리 → 하나의 최종 보고서로 통합
- 잘 맞는 작업: 앱 전체 기능 구현, 대형 리팩토링, 여러 파일 동시 수정, 프론트+백엔드+DB 연결, 테스트 코드 포함 수정, 기존 코드베이스 구조 분석, 프로젝트 전체 버그 검사, 대규모 보안 감사, 수백 개 파일 마이그레이션, 프레임워크/API 교체, 여러 출처 교차 검증 조사
- 제한: 동시에 실행 가능한 에이전트 최대 16개, 한 번의 Workflow에서 생성 가능한 총 에이전트 최대 1,000개
- 이용 가능 환경: Claude Code 2.1.154 이상, Claude 유료 요금제, Anthropic API, Amazon Bedrock, Google Cloud Vertex AI, Microsoft Foundry
- 사용량 확인: `/workflows` 화면에서 각 에이전트의 토큰 사용량을 볼 수 있습니다.

작업 분해를 직접 지시하는 프롬프트:
```
이 작업은 여러 파일과 여러 하위 작업으로 나뉠 가능성이 큽니다.
먼저 전체 작업을 다음 기준으로 분해해주세요.
1. 구조 파악
2. 수정이 필요한 파일 목록
3. 각 파일별 변경 목적
4. 구현 순서
5. 테스트 계획
6. 실패 가능성이 높은 지점
그다음 각 하위 작업을 독립적으로 처리하고,
마지막에 전체 통합 검수를 진행해주세요.
```

#### Ultracode 켜기

Ultracode는 Claude Code의 실행 설정으로, 모델 effort를 `xhigh`로 두고 중요한 작업마다 Dynamic Workflow 필요 여부를 판단해 자동으로 구성합니다. 하나의 요청도 프로젝트 구조 분석, 코드 수정, 결과 검증 등으로 나눠 처리할 수 있습니다.

- 설정: `/effort ultracode`
- 적용 범위: 현재 Claude Code 세션에만 적용됩니다.
- 비용: 일반적인 낮은 effort보다 토큰을 더 쓰고 작업 시간이 길어질 수 있습니다. 작은 작업에 쓰면 사용량만 크게 먹으니 작업 단위가 충분히 클 때만 씁니다.

#### Subagent 생성 제어하기

Opus 4.8은 기본적으로 subagent를 덜 생성할 수 있어, 언제 분산 처리할지를 명확히 써줍니다.

직접 처리하게 할 때:
```
이 작업은 범위가 작습니다.
별도의 subagent를 만들지 말고,
현재 보고 있는 파일 안에서 직접 처리해주세요.
```

하위 작업으로 나누게 할 때:
```
이 작업은 여러 파일과 여러 책임 영역으로 나뉩니다.
프론트엔드, 백엔드, 데이터 구조, 테스트를 각각 별도 하위 작업으로 나눠서 검토해주세요.
각 하위 작업의 결과를 마지막에 통합해 최종 수정 계획을 제시해주세요.
```

코드베이스 분석용:
```
파일 탐색, 의존성 확인, 테스트 전략 수립은 병렬로 진행해도 됩니다.
다만 실제 코드 수정은 전체 계획을 제시한 뒤 진행해주세요.
```

#### /deep-research 쓰기

Dynamic Workflows 기반의 Claude Code 내장 Workflow입니다(Opus 4.8 모델 자체 기능이 아닙니다). 질문을 여러 검색 방향으로 나눠 병렬 검색 → 출처 수집 → 교차 검증 → 인용 보고서 작성까지 수행합니다.

- 실행: `/deep-research 조사할 질문`
- 요구사항: WebSearch 도구를 쓸 수 있어야 합니다.

### 5. 작업 유형별 템플릿

#### 프론트엔드·디자인

Opus 4.8은 기본 디자인 취향이 강하게 나타날 수 있어, "예쁘게 해줘"만 주면 비슷한 톤으로 수렴합니다. 색상·폰트·레이아웃까지 명확히 지정합니다.

나쁜 예시:
```
깔끔하고 미니멀하게 만들어줘.
크림색은 쓰지 마.
AI스럽게 만들지 마.
```

좋은 예시:
```
이 UI는 개발자용 SaaS 대시보드입니다.
디자인 방향:
- 배경: #0B0F17 계열의 어두운 네이비
- 카드: #111827
- 텍스트: #F9FAFB / 보조 텍스트 #9CA3AF
- 액센트: #60A5FA
- 폰트: Inter 대신 더 기술적이고 단정한 sans-serif 계열
- 코너 반경: 16px 이하
- 느낌: 엔터프라이즈 SaaS, 개발자 도구, 고신뢰
피해야 할 것:
- 크림색 에디토리얼 스타일
- 보라색 그라데이션 남발
- 의미 없는 3D 아이콘
- 과한 그림자
```

방향이 정해지지 않았다면 옵션부터 뽑게 합니다:
```
구현하기 전에 이 브리프에 맞는 4가지 비주얼 방향을 먼저 제안해주세요.
각 방향마다 아래 항목을 포함해주세요.
1. 배경 hex
2. 액센트 hex
3. 폰트 방향
4. 레이아웃 구조
5. 이 방향이 적합한 이유
제가 하나를 고르면, 선택한 방향만 구현해주세요.
```

#### 코드 리뷰 — 발견과 필터링을 나누기

"중요한 것만 보고하라"를 너무 문자 그대로 따르면 낮은 심각도 버그를 조용히 빼버릴 수 있습니다. 두 단계로 나눕니다.

1단계 발견 (커버리지 우선):
```
이 단계의 목표는 커버리지입니다.
확신이 낮거나 저심각도로 보이는 것도 포함해서,
발견한 모든 잠재 이슈를 보고해주세요.
각 이슈마다 아래를 함께 적어주세요.
1. 이슈 내용
2. 영향 범위
3. 확신도: 높음/중간/낮음
4. 심각도: 높음/중간/낮음
5. 재현 또는 검증 방법
이 단계에서는 중요도 기준으로 필터링하지 마세요.
후속 단계에서 제가 우선순위를 정하겠습니다.
```

2단계 필터링:
```
방금 찾은 이슈 중에서 실제 사용자 문제, 테스트 실패, 데이터 손상, 보안 리스크로 이어질 수 있는 것만 우선순위화해주세요.
순수한 네이밍 취향이나 스타일 문제는 제외해주세요.
```

#### 긴 문서 분석

단순 요약보다 구조화된 분석을 시킵니다.

```
목표:
아래 문서를 실무에서 바로 쓸 수 있는 가이드로 바꾸고 싶습니다.
작업 방식:
1. 핵심 주장 5개를 뽑아주세요.
2. 각 주장마다 실무 적용법을 정리해주세요.
3. 놓치기 쉬운 주의사항을 따로 표시해주세요.
4. 기존 상식과 다른 부분이 있다면 강조해주세요.
5. 마지막에 바로 복붙 가능한 템플릿을 만들어주세요.
성공 기준:
- 원문에 없는 내용을 과하게 추측하지 않아야 합니다.
- 실행 가능한 형태여야 합니다.
- 초보자도 이해할 수 있어야 합니다.
- 중요한 조건과 예외를 빠뜨리면 안 됩니다.
문서:
[여기에 원문 붙여넣기]
```

#### 콘텐츠 기획 (인스타 캐러셀)

```
목표:
아래 소스를 인스타그램 캐러셀 콘텐츠로 만들고 싶습니다.
타깃:
AI를 실무에 쓰고 싶은 대학생, 크리에이터, 1인 사업가입니다.
너무 기술적으로 어려우면 이탈할 수 있습니다.
원하는 결과물:
- 총 8~10장 캐러셀
- 1장: 후킹 표지
- 2장: 공감 진입
- 3~7장: 핵심 정보
- 8장: 사용 원칙 또는 주의사항
- 9장: CTA

- 해시태그 3~5개
- 댓글 DM용 노션 가이드까지 작성

작업 방식:
1. 핵심 메시지를 먼저 뽑아주세요.
2. 후킹 각도를 정해주세요.
3. 슬라이드별 카피를 작성해주세요.
4. 캡션과 해시태그를 작성해주세요.
5. 댓글 DM용 가이드를 별도로 만들어주세요.
소스:
[여기에 원문 붙여넣기]

### 6. 비용·토큰 아끼기

기본 원칙은 짧은 작업 Low/Medium, 일반 작업 High, 코딩·에이전트 X High, Max는 테스트용, Ultra Code는 대형 작업용입니다. 여러 턴으로 질질 끌기보다 첫 프롬프트에 맥락을 충분히 넣고, 결과가 이상하면 프롬프트를 덧붙이기 전에 effort부터 점검합니다.

범위를 묶어두는 문장들:
```
작업 범위를 벗어난 제안은 하지 마세요.
현재 목표를 달성하는 데 필요한 내용만 처리해주세요.
```
```
먼저 계획만 제시해주세요.
제가 승인하기 전까지 실제 수정은 하지 마세요.
```
```
불필요한 배경 설명은 생략하고,
결정에 필요한 정보와 실행 단계만 제공해주세요.
```
```
가능한 한 적은 파일만 수정해주세요.
수정하지 않아도 되는 파일은 건드리지 마세요.
```

토큰 계산 시 참고할 점:
- Opus 4.7부터 쓰인 새 토크나이저는 이전 모델 대비 같은 텍스트에 최대 35% 더 많은 토큰을 쓸 수 있고, Opus 4.8도 같은 토크나이저를 씁니다. 4.7 이전 모델과 비교하면 사용량이 늘 수 있습니다. 4.7과 4.8 사이의 차이는 토크나이저보다 effort 설정 같은 다른 요인의 영향이 더 큽니다.
- Dynamic Workflows와 Ultracode는 여러 에이전트를 실행하므로 일반 대화보다 의미 있게 많은 토큰을 쓸 수 있습니다. 평균 증가 배수는 공개되지 않았으니 `/workflows` 화면에서 확인하며 관리합니다.

### 7. Opus 4.7 → 4.8 전환 체크리스트

**제거하거나 줄일 것** — 예전 모델 보완용 "anti-laziness" 프롬프트는 Opus 4.8에서 오히려 과한 반응을 부를 수 있습니다.
```
계속 진행해.
멈추지 마.
반드시 끝까지 해.
도구 호출 3번마다 보고해.
게으르게 굴지 마.
```

**추가하면 좋은 것**:
```
작업 범위를 명확히 지켜주세요.
불확실한 내용은 추측하지 말고 확인 필요로 표시해주세요.
```
```
이 지시는 모든 섹션에 적용됩니다.
첫 번째 항목에만 적용하지 마세요.
```
```
수정 전에는 계획을 먼저 보여주세요.
수정 후에는 변경 사항과 남은 리스크를 구분해주세요.
```
```
단순 스타일 취향이 아니라 실제 오류, 사용자 문제, 테스트 실패 가능성이 있는 항목을 우선 보고해주세요.
```

### 8. API 개발자용: 중간 system 메시지와 Fast Mode

#### 대화 중 system 메시지 바꾸기

Opus 4.8의 Messages API는 `messages` 배열 중간에 `system` 역할의 메시지를 넣을 수 있습니다. 에이전트가 긴 작업을 하는 도중 전체 프롬프트를 다시 보내지 않고 지침(예: 토큰 예산, 실행 환경 정보, 새 제약 조건)을 바꿀 수 있어 Prompt Cache가 유지되고 반복 작업의 입력 비용이 줄어듭니다.

#### Fast Mode

Opus 모델을 더 빠른 출력 속도로 쓰는 기능입니다. Opus 4.8 Fast Mode는 초당 출력 토큰 속도가 최대 2.5배 빠르고, 가격은 Opus 4.7 Fast Mode의 3분의 1로 인하됐습니다.

| 항목 | 값 |
|---|---|
| 입력 | 100만 토큰당 10달러 |
| 출력 | 100만 토큰당 50달러 |
| 일반 Opus 4.8 대비 | 토큰 단가 2배 |

빠른 응답이 꼭 필요한 경우에만 쓰는 것이 비용 효율적입니다.

### 9. 마스터 프롬프트 저장해두기

아래 템플릿 하나만 저장해두면 대부분의 작업에 응용할 수 있습니다.

```
목표:
[내가 달성하고 싶은 최종 결과를 작성]
현재 상황:
[지금 상태, 배경, 문제점, 관련 파일/문서/소스]
작업 유형:
[콘텐츠 기획 / 코드 수정 / 문서 분석 / 디자인 / 코드 리뷰 / 리서치 중 선택]
원하는 결과물:
[형식, 분량, 톤, 파일 형태, 사용 목적]
성공 기준:
1. [좋은 결과의 기준 1]
2. [좋은 결과의 기준 2]
3. [좋은 결과의 기준 3]
작업 방식:
1. 먼저 현재 상황을 분석해주세요.
2. 바로 실행하지 말고 작업 계획을 제시해주세요.
3. 필요한 경우 작업을 작은 단위로 나눠주세요.
4. 실행 후 결과물을 검수해주세요.
5. 마지막에 변경 사항, 남은 리스크, 다음 액션을 구분해서 정리해주세요.
도구 사용 기준:
- 최신 정보가 필요하면 먼저 확인해주세요.
- 파일/코드가 있으면 추측하지 말고 실제 내용을 확인해주세요.

범위 제한:

출력 방식:

### 시나리오

- **로그인 오류 디버깅** → effort를 X High로 올리고 3절 기본 작업 루틴 템플릿에 기능명만 채워 넣으면 구조 파악부터 검수 체크리스트까지 한 번에 나옵니다.
- **인스타 캐러셀 기획** → effort High + 5절 콘텐츠 기획 프롬프트에 소스만 붙여넣으면 8~10장 슬라이드 카피, 캡션, 댓글 DM 가이드까지 완성됩니다.
- **결제 플로우처럼 프론트/백엔드/DB를 다 건드리는 대형 작업** → `/effort ultracode`를 켜고 4절 Dynamic Workflows 분해 프롬프트로 작업을 나눈 뒤 단계별로 승인하며 진행합니다.
- **대규모 코드베이스 보안 감사** → Claude Code에서 `/effort ultracode`를 설정하고 `/deep-research: 프로젝트 전체의 보안 취약점을 감사해줘.`처럼 요청하면, 여러 에이전트가 병렬로 코드 분석·취약점 탐지·관련 정보 검색·교차 검증을 수행한 뒤 최종 보고서를 만듭니다.
- **복잡한 금융 보고서 작성 (웹/API)** → Claude 웹에서 Opus 4.8을 고르고 Effort를 'high' 또는 'extra'로 올려 깊이 있게 분석합니다. API에서는 effort를 조절하고, 덜 중요한 단계에는 Fast Mode를 써서 비용과 속도를 맞춥니다.
- **실시간 지침 변경이 필요한 에이전트 서비스 (API)** → 사용자가 특정 기능을 요청하면 대화 중간에 `system` 메시지를 넣어 그 기능에 필요한 지침·제약(토큰 예산, 실행 환경 정보 등)을 갱신합니다.

## 💡 아이디어

- **개인 맞춤형 코딩 도우미**: 향상된 코딩 능력과 Dynamic Workflows를 결합해, 사용자의 코딩 스타일·자주 쓰는 라이브러리·프로젝트 구조에 맞춘 코드 제안·리팩토링·버그 수정 자동화를 만듭니다. 대규모 리팩토링이나 복잡한 기능 구현에는 Ultracode로 자동화 수준을 높입니다.
- **시장 분석 보고서 자동 생성**: `/deep-research`와 Opus 4.8의 금융 분석 능력을 묶어 특정 상품·시장 동향 데이터를 수집하고 여러 출처를 교차 검증한 심층 보고서를 만듭니다. 수집·분석·작성 단계를 Dynamic Workflows로 분산하면 효율이 올라갑니다.

## 주의사항

- **Max는 기본값이 아닙니다.** High/X High로 부족할 때만 테스트하세요. 토큰 대비 효용이 낮아지고 과도하게 생각할 수 있습니다.
- **Ultracode·Dynamic Workflows는 토큰을 많이 씁니다.** 작은 작업에 쓰지 말고, `/workflows` 화면에서 에이전트별 사용량을 확인하세요. Ultracode는 현재 세션에만 적용됩니다.
- **Fast Mode는 토큰 단가가 일반 모드의 2배**입니다. 빠른 응답이 꼭 필요할 때만 쓰세요.
- **anti-laziness 프롬프트는 지우세요.** "계속 진행해", "게으르게 굴지 마" 같은 문장은 Opus 4.8에서 과한 반응을 유발할 수 있습니다.
- **코드 리뷰는 발견·필터링 2단계로.** "중요한 것만 보고해"만 쓰면 저심각도 버그가 조용히 누락될 수 있습니다.
- **도구가 필요하면 명시하세요.** 자체 추론을 먼저 하려는 경향이 있어, 최신 정보·실제 파일 확인이 필요한 작업은 "먼저 확인하라"고 적어야 합니다.
- **벤치마크 해석에 주의하세요.** Terminal-Bench 2.1 등 일부 항목에서는 GPT-5.5가 더 높았습니다.
- **토큰 사용량 비교 시** Opus 4.7 이전 모델과는 토크나이저 차이(최대 35%)가 있다는 점을 감안하세요.
