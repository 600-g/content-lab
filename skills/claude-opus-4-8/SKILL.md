# Opus 4.8 풀세팅 마스터하기 (합병됨)

## 이게 뭔가요?

Opus 4.8은 단순히 '더 좋은 Claude'가 아니라, **설정값을 함께 바꿔야 성능이 극대화되는 모델**입니다. 이전 모델처럼 프롬프트만 잘 쓰면 되는 게 아니라, 아래 3가지를 함께 봐야 합니다.

| 구분 | 의미 | 실전 영향 |
|---|---|---|
| Model | Opus 4.8 자체 성능 | 기본 추론력, 코딩력, 글쓰기 품질 |
| Effort | 얼마나 깊게 생각할지 | 속도, 비용, 품질 차이 |
| Workflow | 작업을 어떻게 쪼개서 실행할지 | Claude Code 대형 작업 성능 |

모델만 바꾸면 체감이 약할 수 있고, **effort와 프롬프트 구조까지 같이 바꿔야** 성능이 체감됩니다. 이번 업데이트에서 특히 중요한 포인트는 4가지입니다.

- **Effort 설정**이 핵심 레버가 됨
- 프롬프트를 **더 문자 그대로 해석**함
- **도구 호출보다 먼저 자체 추론**하려는 경향이 있음
- 코딩·디자인·리뷰 작업에서 세팅 방식이 달라짐

Claude 및 Claude Code에서 사용합니다. 별도 유료 도구는 필요 없고, Claude Opus 4.8 모델 자체 접근 권한만 있으면 됩니다.

💰 유료 필요: Claude Opus 4.8 (최신 모델)
✅ 무료 대안: 현재는 모델 자체의 설정 최적화가 핵심이므로, 다른 모델로 대체하기보다 이 가이드의 **프롬프트 구조화** 원칙을 적용하는 것이 중요합니다.

## 따라하기

### 1. 작업별 Effort 세팅표 확인하기

Opus 4.8에서 가장 먼저 만져야 하는 건 effort입니다.

| 작업 유형 | 추천 effort | 이유 |
|---|---|---|
| 짧은 문장 수정 | Low / Medium | 빠른 응답이 더 중요 |
| 번역, 짧은 요약 | Medium | 비용과 속도 균형 |
| 콘텐츠 기획 | High | 맥락 이해와 구조화 필요 |
| 긴 문서 분석 | High / X High | 놓치는 정보 줄이기 |
| 코드 디버깅 | X High | 원인 추적 필요 |
| 복수 파일 수정 | X High | 파일 간 연결성 확인 필요 |
| 대형 리팩토링 | X High / Max | 구조적 판단 필요 |
| 앱 전체 구현 | Ultra Code | workflow·subagent 활용 |
| 코드 리뷰 | X High | 버그 탐지 깊이 필요 |
| 단순 질문 답변 | Low / Medium | 과추론 방지 |

### 2. Effort 레벨별 사용법 익히기

**Low** — 짧고 범위가 명확한 작업에만 사용. 복잡한 작업을 Low로 돌리면 표면적인 답만 나올 수 있습니다.
```
이 문장만 자연스럽게 바꿔줘.
아래 문장을 3줄로 요약해줘.
```

**Medium** — 비용과 속도가 중요한 반복 작업에 적합.
```
아래 고객 리뷰 30개를 긍정/부정/개선요청으로 분류해줘.
아래 문장을 인스타 캡션용으로 조금 더 자연스럽게 다듬어줘.
```

**High** — 대부분의 실무 작업 기본값.
```
아래 내용을 바탕으로 인스타 캐러셀 기획안과 캡션을 만들어줘.
아래 시장조사 내용을 요약하고, 실무자가 바로 실행할 액션 아이템으로 바꿔줘.
```

**X High** — 코딩, 에이전트, 복잡한 분석 작업의 기본값.
```
이 코드베이스에서 로그인 오류가 발생하는 원인을 추적하고 수정 계획을 세워줘.
아래 5개 문서를 비교해서 공통 인사이트와 충돌하는 내용을 정리해줘.
```

**Max** — 정말 복잡한 작업에서만 테스트. 토큰 증가 대비 효용이 줄어들 수 있고 과도하게 생각할 수 있어, High/X High로 부족할 때 올리는 옵션입니다.

**Ultra Code** — Claude Code에서 대형 작업을 맡길 때 쓰는 고강도 모드.
```
이 프로젝트에 결제 플로우를 추가하고,
프론트엔드/백엔드/DB/에러 처리/테스트까지
전체 구현 계획을 세운 뒤 단계별로 진행해줘.
```
작은 작업에 쓰면 사용량만 크게 먹으니 작업 단위가 충분히 클 때만 사용합니다.

### 3. 기본 프롬프트 구조 템플릿 쓰기

Opus 4.8에서는 "대충 해줘"보다 목표·맥락·성공 기준을 분명히 주는 게 중요합니다.

```
목표:
[이 작업을 통해 얻고 싶은 최종 결과]
현재 상황:
[지금 상태, 배경, 문제점]
원하는 결과물:
[형식, 분량, 톤, 파일 형태, 사용 목적]
성공 기준:
[좋은 결과라고 판단할 기준]
작업 방식:
1. 먼저 현재 상황을 진단해주세요.
2. 그다음 작업 계획을 제시해주세요.
3. 필요한 경우 단계별로 실행해주세요.
4. 마지막에 검수 체크리스트를 제공해주세요.
주의사항:
[금지 표현, 브랜드 톤, 기술 제약, 비용 제약 등]
```

### 4. "하지 마"보다 "이렇게 해"라고 쓰기

Opus 4.8은 지시를 문자 그대로 잘 따릅니다. 부정 지시만 잔뜩 넣는 것보다 원하는 방향을 구체적으로 알려주는 게 안정적입니다.

나쁜 예시:
```
너무 장황하지 않게 해줘.
AI 티 나게 쓰지 마.
뻔하게 만들지 마.
```

좋은 예시:
```
답변은 핵심만 5개 항목으로 정리해주세요.
각 항목은 2문장 이내로 작성해주세요.
실무자가 바로 실행할 수 있는 표현을 사용해주세요.
추상적인 조언보다 구체적인 행동 지침을 우선해주세요.
```

### 5. "왜"를 같이 주기

Opus 4.8은 목적을 알면 결과가 좋아집니다.

나쁜 예시 → 좋은 예시 (카피 작업):
```
이 문장은 인스타그램 캐러셀 첫 장에 들어갈 후킹 문장입니다.
목표는 사용자가 스크롤을 멈추고 다음 장을 넘기게 만드는 것입니다.
너무 과장된 표현은 피하고, "나도 해당되나?"라는 느낌이 들게 바꿔주세요.
```

나쁜 예시 → 좋은 예시 (디자인 작업):
```
이 디자인은 AI 실무 팁을 공유하는 인스타 캐러셀 표지입니다.
타깃은 대학생, 크리에이터, 1인 사업가입니다.
너무 개발자 문서처럼 딱딱하면 안 되고,
저장하고 싶은 프리미엄 가이드 느낌이 나야 합니다.
어두운 배경, 큰 타이포, 작은 라벨, 명확한 CTA 구조로 제안해주세요.
```

### 6. 응답 길이 조절하기

Opus 4.8은 작업 복잡도를 보고 스스로 응답 길이를 조절하는 경향이 있어, 원하는 길이를 명확히 써주는 게 좋습니다.

짧게 받고 싶을 때:
```
답변은 5줄 이내로 작성해주세요.
배경 설명은 생략하고, 바로 실행할 수 있는 항목만 주세요.
예시는 1개만 포함해주세요.
```

깊게 받고 싶을 때:
```
표면적인 요약이 아니라,
원인 → 구조 → 실행 방안 → 주의사항 순서로 분석해주세요.
각 항목마다 실무 예시를 포함해주세요.
```

콘텐츠용으로 받고 싶을 때:
```
인스타그램 저장형 콘텐츠에 맞게 작성해주세요.
문장은 짧게 끊고, 한 문단은 2~3줄을 넘기지 마세요.
전문 용어는 필요한 경우에만 쓰고, 바로 아래에 쉽게 풀어 설명해주세요.
```

### 7. 도구 사용이 필요하면 명시하기

Opus 4.8은 도구를 무조건 먼저 쓰기보다 자체 추론으로 해결하려는 경향이 있습니다. 최신 정보·파일 확인·코드베이스 분석이 필요하면 조건을 명시하세요.

최신 정보 확인용:
```
이 작업은 최신 정보 확인이 중요합니다.
답변하기 전에 공식 문서 또는 신뢰할 수 있는 최신 자료를 먼저 확인해주세요.
확인한 정보와 추정한 정보를 구분해서 작성해주세요.
```

코드 작업용:
```
답변하기 전에 관련 파일을 먼저 읽어주세요.
추측으로 원인을 단정하지 말고,
실제 코드에서 확인된 내용과 가능성 있는 가설을 구분해주세요.
```

자료 분석용:
```
첨부된 문서를 먼저 기준 자료로 삼아주세요.
문서에 없는 내용은 외부 지식으로 보완하되,
문서 기반 내용과 보완 내용을 구분해주세요.
```

### 8. Thinking 설정 이해하기

Opus 4.8에서 thinking은 기본적으로 꺼져 있을 수 있습니다. 복잡한 추론(버그 원인 분석, 문서 간 충돌 검토, 장기 계획 수립, 법률·계약·비용 검토, 대규모 코드 수정 전 설계)에서는 adaptive thinking을 켜는 방향을 고려하되, 지연 시간이 늘 수 있으니 아무 때나 켜지 않습니다.

깊게 생각해야 할 때:
```
이 작업은 다단계 추론이 필요합니다.
답변하기 전에 문제 구조를 신중하게 검토하고,
확실한 내용과 확인이 필요한 내용을 구분해주세요.
```

빠르게 답이 필요할 때:
```
이 작업은 단순 조회성 작업입니다.
불필요하게 길게 추론하지 말고,
바로 핵심 답변만 제공해주세요.
```

### 9. Claude Code 기본 작업 루틴 쓰기

처음부터 "다 고쳐줘"라고 던지지 말고 아래 루틴으로 진행합니다: 현재 구조 파악 → 문제 원인 후보 정리 → 수정 계획 작성 → 필요한 파일만 수정 → 테스트 또는 검증 → 남은 리스크 정리.

```
목표:
이 프로젝트에서 [기능명/문제명]을 해결하고 싶습니다.
작업 방식:
1. 먼저 관련 파일과 현재 구조를 파악해주세요.
2. 아직 코드를 수정하지 말고, 변경 계획을 먼저 제시해주세요.
3. 변경 범위가 과도하면 더 작은 단위로 쪼개주세요.
4. 승인 후 필요한 파일만 수정해주세요.
5. 수정 후 테스트 방법과 검수 체크리스트를 제공해주세요.
성공 기준:
- 기존 기능이 깨지지 않아야 합니다.
- 수정 이유가 명확해야 합니다.
- 실제 실행 가능한 코드여야 합니다.
- 남은 리스크가 있다면 숨기지 말고 알려주세요.
```

### 10. Dynamic Workflows 사용하기

앱 전체 기능 구현, 대형 리팩토링, 여러 파일 동시 수정, 프론트+백엔드+DB 연결, 테스트 코드 포함 수정, 기존 코드베이스 구조 분석에 적합합니다.

```
이 작업은 여러 파일과 여러 하위 작업으로 나뉠 가능성이 큽니다.
먼저 전체 작업을 다음 기준으로 분해해주세요.
1. 구조 파악
2. 수정이 필요한 파일 목록
3. 각 파일별 변경 목적
4. 구현 순서
5. 테스트 계획
6. 실패 가능성이 높은 지점
그다음 각 하위 작업을 독립적으로 처리하고,
마지막에 전체 통합 검수를 진행해주세요.
```

### 11. Subagent 생성 제어하기

Opus 4.8은 기본적으로 subagent를 덜 생성할 수 있어, "언제 분산 처리할지"를 명확히 써줍니다.

직접 처리하게 할 때:
```
이 작업은 범위가 작습니다.
별도의 subagent를 만들지 말고,
현재 보고 있는 파일 안에서 직접 처리해주세요.
```

하위 작업으로 나누게 할 때:
```
이 작업은 여러 파일과 여러 책임 영역으로 나뉩니다.
프론트엔드, 백엔드, 데이터 구조, 테스트를 각각 별도 하위 작업으로 나눠서 검토해주세요.
각 하위 작업의 결과를 마지막에 통합해 최종 수정 계획을 제시해주세요.
```

코드베이스 분석용:
```
파일 탐색, 의존성 확인, 테스트 전략 수립은 병렬로 진행해도 됩니다.
다만 실제 코드 수정은 전체 계획을 제시한 뒤 진행해주세요.
```

### 12. 프론트엔드·디자인 작업 세팅하기

Opus 4.8은 기본 디자인 취향이 강하게 나타날 수 있어, "예쁘게 해줘"만 주면 비슷한 톤으로 수렴합니다. 색상·폰트·레이아웃까지 명확히 지정하세요.

나쁜 예시:
```
깔끔하고 미니멀하게 만들어줘.
크림색은 쓰지 마.
AI스럽게 만들지 마.
```

좋은 예시:
```
이 UI는 개발자용 SaaS 대시보드입니다.
디자인 방향:
- 배경: #0B0F17 계열의 어두운 네이비
- 카드: #111827
- 텍스트: #F9FAFB / 보조 텍스트 #9CA3AF
- 액센트: #60A5FA
- 폰트: Inter 대신 더 기술적이고 단정한 sans-serif 계열
- 코너 반경: 16px 이하
- 느낌: 엔터프라이즈 SaaS, 개발자 도구, 고신뢰
피해야 할 것:
- 크림색 에디토리얼 스타일
- 보라색 그라데이션 남발
- 의미 없는 3D 아이콘
- 과한 그림자
```

옵션을 먼저 뽑게 하는 방식:
```
구현하기 전에 이 브리프에 맞는 4가지 비주얼 방향을 먼저 제안해주세요.
각 방향마다 아래 항목을 포함해주세요.
1. 배경 hex
2. 액센트 hex
3. 폰트 방향
4. 레이아웃 구조
5. 이 방향이 적합한 이유
제가 하나를 고르면, 선택한 방향만 구현해주세요.
```

### 13. 코드 리뷰 프롬프트 나누기

"중요한 것만 보고하라"를 너무 문자 그대로 따르면 낮은 심각도 버그를 조용히 빼버릴 수 있습니다. **발견 단계**와 **필터링 단계**를 나누세요.

발견 단계 (커버리지 우선):
```
이 단계의 목표는 커버리지입니다.
확신이 낮거나 저심각도로 보이는 것도 포함해서,
발견한 모든 잠재 이슈를 보고해주세요.
각 이슈마다 아래를 함께 적어주세요.
1. 이슈 내용
2. 영향 범위
3. 확신도: 높음/중간/낮음
4. 심각도: 높음/중간/낮음
5. 재현 또는 검증 방법
이 단계에서는 중요도 기준으로 필터링하지 마세요.
후속 단계에서 제가 우선순위를 정하겠습니다.
```

후속 필터링 단계:
```
방금 찾은 이슈 중에서 실제 사용자 문제, 테스트 실패, 데이터 손상, 보안 리스크로 이어질 수 있는 것만 우선순위화해주세요.
순수한 네이밍 취향이나 스타일 문제는 제외해주세요.
```

### 14. 긴 문서 분석 프롬프트 쓰기

단순 요약보다 "구조화된 분석"을 시킵니다.

```
목표:
아래 문서를 실무에서 바로 쓸 수 있는 가이드로 바꾸고 싶습니다.
작업 방식:
1. 핵심 주장 5개를 뽑아주세요.
2. 각 주장마다 실무 적용법을 정리해주세요.
3. 놓치기 쉬운 주의사항을 따로 표시해주세요.
4. 기존 상식과 다른 부분이 있다면 강조해주세요.
5. 마지막에 바로 복붙 가능한 템플릿을 만들어주세요.
성공 기준:
- 원문에 없는 내용을 과하게 추측하지 않아야 합니다.
- 실행 가능한 형태여야 합니다.
- 초보자도 이해할 수 있어야 합니다.
- 중요한 조건과 예외를 빠뜨리면 안 됩니다.
문서:
[여기에 원문 붙여넣기]
```

### 15. 콘텐츠 기획 프롬프트 쓰기

인스타 캐러셀용으로 가장 좋은 템플릿입니다.

```
목표:
아래 소스를 인스타그램 캐러셀 콘텐츠로 만들고 싶습니다.
타깃:
AI를 실무에 쓰고 싶은 대학생, 크리에이터, 1인 사업가입니다.
너무 기술적으로 어려우면 이탈할 수 있습니다.
원하는 결과물:
- 총 8~10장 캐러셀
- 1장: 후킹 표지
- 2장: 공감 진입
- 3~7장: 핵심 정보
- 8장: 사용 원칙 또는 주의사항
- 9장: CTA
- 600자 이상 스토리텔링 캡션
- 해시태그 3~5개
- 댓글 DM용 노션 가이드까지 작성
성공 기준:
- 첫 장에서 저장하고 싶어야 합니다.
- 한 슬라이드에는 한 메시지만 들어가야 합니다.
- 중간 슬라이드는 실전 팁 중심이어야 합니다.
- 캡션은 캐러셀 내용 반복이 아니라 "왜 이걸 공유하는지"를 담아야 합니다.
- 댓글 CTA가 자연스러워야 합니다.
작업 방식:
1. 핵심 메시지를 먼저 뽑아주세요.
2. 후킹 각도를 정해주세요.
3. 슬라이드별 카피를 작성해주세요.
4. 캡션과 해시태그를 작성해주세요.
5. 댓글 DM용 가이드를 별도로 만들어주세요.
소스:
[여기에 원문 붙여넣기]
```

### 16. 비용·토큰 절약 운영법 적용하기

기본 원칙: 짧은 작업은 Low/Medium, 일반 작업은 High, 코딩·에이전트는 X High, Max는 테스트용, Ultra Code는 대형 작업용. 여러 턴으로 질질 끌기보다 첫 프롬프트에 맥락을 충분히 넣고, 결과가 이상하면 프롬프트를 덧붙이기 전에 effort부터 점검합니다.

```
작업 범위를 벗어난 제안은 하지 마세요.
현재 목표를 달성하는 데 필요한 내용만 처리해주세요.
```
```
먼저 계획만 제시해주세요.
제가 승인하기 전까지 실제 수정은 하지 마세요.
```
```
불필요한 배경 설명은 생략하고,
결정에 필요한 정보와 실행 단계만 제공해주세요.
```
```
가능한 한 적은 파일만 수정해주세요.
수정하지 않아도 되는 파일은 건드리지 마세요.
```

### 17. Opus 4.7 → 4.8 전환 체크리스트 적용하기

**제거하거나 줄일 것** — 아래 같은 "anti-laziness" 프롬프트는 예전 모델 보완용이라 Opus 4.8에서는 오히려 과해질 수 있습니다.
```
계속 진행해.
멈추지 마.
반드시 끝까지 해.
도구 호출 3번마다 보고해.
게으르게 굴지 마.
```

**추가하면 좋은 것**:
```
작업 범위를 명확히 지켜주세요.
불확실한 내용은 추측하지 말고 확인 필요로 표시해주세요.
```
```
이 지시는 모든 섹션에 적용됩니다.
첫 번째 항목에만 적용하지 마세요.
```
```
수정 전에는 계획을 먼저 보여주세요.
수정 후에는 변경 사항과 남은 리스크를 구분해주세요.
```
```
단순 스타일 취향이 아니라 실제 오류, 사용자 문제, 테스트 실패 가능성이 있는 항목을 우선 보고해주세요.
```

### 18. 최종 마스터 프롬프트 저장하기

아래 템플릿 하나만 저장해두면 대부분의 작업에 응용할 수 있습니다.

```
목표:
[내가 달성하고 싶은 최종 결과를 작성]
현재 상황:
[지금 상태, 배경, 문제점, 관련 파일/문서/소스]
작업 유형:
[콘텐츠 기획 / 코드 수정 / 문서 분석 / 디자인 / 코드 리뷰 / 리서치 중 선택]
원하는 결과물:
[형식, 분량, 톤, 파일 형태, 사용 목적]
성공 기준:
1. [좋은 결과의 기준 1]
2. [좋은 결과의 기준 2]
3. [좋은 결과의 기준 3]
작업 방식:
1. 먼저 현재 상황을 분석해주세요.
2. 바로 실행하지 말고 작업 계획을 제시해주세요.
3. 필요한 경우 작업을 작은 단위로 나눠주세요.
4. 실행 후 결과물을 검수해주세요.
5. 마지막에 변경 사항, 남은 리스크, 다음 액션을 구분해서 정리해주세요.
도구 사용 기준:
- 최신 정보가 필요하면 먼저 확인해주세요.
- 파일/코드가 있으면 추측하지 말고 실제 내용을 확인해주세요.
- 확인한 내용과 추정한 내용을 구분해주세요.
범위 제한:
- 이번 목표와 무관한 확장은 하지 마세요.
- 불필요한 리팩토링이나 과한 제안은 피해주세요.
- 다만 실제 오류나 리스크가 보이면 별도로 알려주세요.
출력 방식:
- 핵심부터 말해주세요.
- 표나 체크리스트를 적극 사용해주세요.
- 바로 복붙 가능한 템플릿이 필요하면 코드블록으로 제공해주세요.
```

## 활용 예시

**상황별 빠른 선택표**

| 상황 | 추천 설정 | 프롬프트 핵심 |
|---|---|---|
| 단순 요약 | Medium | 짧게, 핵심만 |
| 캐러셀 기획 | High | 타깃, 후킹, CTA |
| 노션 가이드 | High / X High | 구조, 템플릿, 실전 예시 |
| 코드 디버깅 | X High | 원인 후보, 검증, 수정 |
| 대형 기능 구현 | X High / Ultra Code | 계획 먼저, 단계 실행 |
| 코드 리뷰 | X High | 발견과 필터링 분리 |
| UI 디자인 | High / X High | 팔레트·폰트·레이아웃 명시 |
| 최신 정보 리서치 | High | 도구 사용 조건 명시 |
| 비용 민감 반복 작업 | Medium | 범위 제한, 짧은 출력 |
| 복잡한 의사결정 | X High / Max | 기준표, 리스크, 우선순위 |

- 로그인 오류를 디버깅할 때 → effort를 X High로 올리고 "9단계 Claude Code 기본 작업 루틴" 템플릿에 기능명만 채워 넣으면 → 구조 파악부터 검수 체크리스트까지 한 번에 나옵니다.
- 인스타 캐러셀을 기획할 때 → effort High + "15단계 콘텐츠 기획 프롬프트"에 소스만 붙여넣으면 → 8~10장 슬라이드 카피, 캡션, 댓글 DM 가이드까지 완성됩니다.
- 결제 플로우처럼 프론트/백엔드/DB를 다 건드리는 대형 작업 → Ultra Code + "10단계 Dynamic Workflows" 템플릿으로 작업을 분해시킨 뒤 단계별 승인하며 진행합니다.

## 주의사항

- **Max**는 무조건 좋은 게 아니라 High/X High로 부족할 때만 테스트하는 옵션입니다. 토큰 증가 대비 효용이 낮아지고 과도하게 생각할 수 있습니다.
- **Ultra Code**를 작은 작업에 쓰면 사용량만 크게 먹으니 작업 단위가 충분히 클 때만 사용하세요.
- 예전 모델용 "계속 진행해", "게으르게 굴지 마" 같은 anti-laziness 프롬프트는 Opus 4.8에서 오히려 과한 반응을 유발할 수 있으므로 제거하는 게 좋습니다.
- 코드 리뷰 시 "중요한 것만 보고해"라고만 하면 저심각도 버그가 조용히 누락될 수 있으니, 발견 단계와 필터링 단계를 반드시 분리하세요.
