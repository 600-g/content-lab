# 끊긴 자동화 연결 원인 찾아 복구하기

💡 이 스킬은 Gmail 같은 구글 OAuth 연결이 갑자기 끊겨 자동화가 멈췄을 때, **만료 조건 6가지**를 확인하고 **5단계 순서**로 복구한 뒤, 0건이어도 알림이 오는 **침묵 실패 방지 장치**까지 붙이는 스킬입니다.

## 이게 뭔가요?

협찬 메일을 분류해서 초안까지 만들어두는 자동화를 매일 돌리던 작성자의 Gmail 연결이 5월 3일에 끊겼습니다. 자동화가 한 시간쯤 멈춰 있었고, 텔레그램으로 브리핑이 오지 않아서 그제야 알았다고 합니다. 작성자는 「6개월 안 쓰면 끊긴다」는 조건만 알고 있었고, 매일 쓰는 연결이라 해당 없다고 생각했습니다. 찾아보니 6개월은 여러 만료 조건 중 하나일 뿐이었습니다.

이 스킬은 그 경험을 정리한 것입니다. 구글 공식 문서(OAuth 2.0 가이드)에 적힌 만료 조건, 멈췄을 때 확인하는 순서, 그리고 조용히 실패하는 자동화를 바로 알아채는 방법으로 구성됩니다. 특정 AI 도구에 묶인 스킬이 아니라, 구글 OAuth로 Gmail 등에 연결해 쓰는 모든 에이전트·자동화(MCP 연결 포함)에 적용됩니다. 작성자가 구글 연결에서 겪은 일이라 다른 서비스는 화면 이름이 다를 수 있습니다.

### 연결이 끊기는 조건 6가지

| 조건 | 언제 걸리나 |
|---|---|
| 앱이 「테스트」 상태 | 7일마다 만료. 매일 써도 끊깁니다 |
| 6개월 미사용 | 「게시됨」 상태인 앱에만 해당 |
| 비밀번호 변경 | Gmail 권한이 포함된 연결이면 즉시 끊김 |
| 권한 회수 | 구글 계정 설정에서 직접 해제했을 때 |
| 개수 초과 | 계정당 앱당 100개 초과 시 오래된 것부터 무효 |
| 관리자 정책 | 회사 계정에서 관리자가 범위를 제한했을 때 |

- 가장 자주 걸리는 건 첫 줄입니다. 구글 클라우드에서 OAuth를 만들면 기본이 「테스트」 상태이고, 이 상태에서 발급된 연결은 매일 쓰든 말든 7일 뒤에 끊깁니다.
- 개인 자동화는 심사를 받을 이유가 없어서 「테스트」 상태로 그냥 두는 경우가 많습니다.
- 작성자의 앱은 「게시됨」 상태였으니 첫 줄에는 해당하지 않았고, 그래서 더 헷갈렸다고 합니다.
- 「게시됨」이라고 해서 6개월만 신경 쓰면 되는 게 아닙니다. 표의 아래 네 줄(비밀번호 변경·권한 회수·개수 초과·관리자 정책)은 게시 상태에서도 그대로 걸립니다.

## 따라하기

### 멈췄을 때 확인하는 순서

작성자가 복구하면서 밟은 순서 그대로입니다.

1. **에이전트를 새로 켜서 도구 목록 확인** — 해당 도구가 목록에 뜨는지 봅니다. 도구 자체가 안 보이면 설정 문제, 뜨는데 실행이 실패하면 권한 문제입니다.
2. **실패 메시지를 그대로 읽기** — 아래 메시지가 보이면 연결 만료가 맞습니다.

```
invalid_grant
```

```
token expired
```

3. **구글 클라우드 콘솔에서 게시 상태 확인** — 해당 프로젝트의 게시 상태를 봅니다. 「테스트」면 7일 만료를 먼저 의심합니다.
4. **저장해둔 토큰 파일을 지우고 인증을 다시 받기** — 대부분 여기서 복구됩니다. 복구 자체는 십 분도 걸리지 않았다고 합니다.
5. **같은 계정에 걸어둔 다른 연결도 같이 확인** — 원인이 계정 쪽이면 하나만 끊긴 게 아닙니다.

5번을 빼먹으면 며칠 뒤에 또 겪습니다. 작성자는 한 곳만 고치고 넘어갔다가, 같은 계정에 붙여둔 다른 연결에서 한 번 더 같은 일이 났습니다. 원인이 계정 단위면 영향도 계정 단위입니다.

### 멈춘 걸 바로 알아채는 장치 붙이기

한 시간을 그냥 보낸 이유는 복구가 어려워서가 아니라, 멈춘 걸 한 시간 동안 몰랐기 때문입니다. 자동화는 조용히 실패합니다. 성공하면 결과물이 오니까 알지만, 실패하면 아무것도 안 오는데 그건 「오늘 처리할 게 없었나 보다」와 화면상 똑같습니다.

1. 자동화 실행이 끝나면 **처리 건수를 텔레그램으로 받도록** 설정합니다.
2. **0건이어도 보냅니다.** 0건이라도 오는 게 핵심이고, 아무것도 안 오는 날이 이상한 날이 됩니다. 작성자도 이번에 브리핑이 안 와서 알아챘습니다.
3. 알림이 번거로우면 **일주일에 한 번 직접 돌려보는 것**만으로도 대부분 잡힙니다. 7일 만료 주기와 얼추 맞습니다.

### 붙여둔 연결 수 줄이기 (선택)

도구를 하나 붙일 때마다 끊길 수 있는 지점이 하나씩 늘어납니다. 작성자는 설정 파일을 다시 보다가 지금 붙여둔 것만 세어봐도 적지 않다는 걸 체감했다고 합니다. 관리 자체를 줄이는 방향으로 소개된 것이 **LINER Action Search**입니다.

- 연결 하나만 걸어두면 에이전트가 작업 중 필요한 도구를 그때그때 찾아 세팅하고 실행까지 한다고 합니다.
- 도구마다 따로 붙여둘 필요가 없다는 쪽입니다.
- 9월 18일에 출시됐습니다.
- 위 동작은 공식 자료와 데모 기준이며, 작성자도 아직 자기 환경에 붙여보지 못했습니다.

## 활용 예시

- **협찬 메일 자동화가 조용히 멈춘 경우**: 아침 브리핑이 오지 않음 → 에이전트를 새로 켜서 Gmail 도구가 목록에 뜨는지 확인 → 실패 메시지에 `invalid_grant` → 콘솔에서 앱이 「테스트」 상태임을 확인 → 토큰 파일 삭제 후 재인증 → 같은 구글 계정에 붙인 캘린더·드라이브 연결도 함께 점검.
- **0건 알림 설계**: 「오늘 처리 0건」 메시지도 매일 텔레그램으로 받게 해둠 → 메시지가 아예 안 온 날은 곧바로 연결 이상으로 판단하고 위 5단계를 시작.
- **비밀번호를 바꾼 다음 날**: 구글 비밀번호 변경 직후 Gmail 권한이 포함된 연결이 즉시 끊기므로, 변경 당일 자동화를 한 번 수동 실행해서 확인.

## 💡 아이디어

- 자동화 스크립트 마지막에 「처리 N건」을 보내는 한 줄을 공통 템플릿으로 만들어 모든 자동화에 넣어두면, 실패 감지가 자동화 개수와 무관하게 통일됩니다.
- 주 1회 수동 실행을 캘린더 반복 일정으로 등록하면 「테스트」 상태 앱의 7일 만료 주기를 커버할 수 있습니다.
- 붙여둔 연결 목록(서비스·계정·게시 상태·마지막 인증일)을 표로 만들어두면 5단계의 계정 단위 점검이 빨라집니다.

## 주의사항

- 「6개월 미사용」 규칙은 맞지만 유일한 조건이 아닙니다. 「테스트」 상태면 7일, 게시 상태여도 비밀번호 변경·권한 회수·개수 초과·관리자 정책으로 끊깁니다.
- 원인이 계정 단위(비밀번호 변경, 권한 회수 등)면 한 연결만 고치고 끝내지 말고 같은 계정의 다른 연결을 모두 확인해야 합니다.
- LINER Action Search는 새 도구를 찾아 붙이는 단계를 줄이는 것이지, 이미 붙여둔 연결들의 만료까지 대신 관리해주지는 않습니다.
- LINER Action Search에 대한 설명은 공식 자료와 데모 기준이며 작성자가 직접 검증하지 않았습니다. 도입 전 직접 확인이 필요합니다.
- 이 글은 구글 연결 사례라서 다른 서비스는 콘솔 화면 이름과 만료 규칙이 다를 수 있습니다.
